Three rules the flows enforce

  1. The password goes from the browser to HMS_WEB and stops there. SivaComm never receives it.
  2. The verification grant goes from SivaComm to HMS_WEB only. The browser never sees it.
  3. A timeout or outage anywhere is a retryable failure, never a success.

Generated 2026-10-25 from SivaComm commit e93ef60 and HMS_WEB commit 3855320.

1. Password reset with SivaComm

SivaComm:Enabled = true in HMS_WEB's config file. Calls marked “signed” carry an HMAC signature made with the key id and secret held in both config files.

2. Password reset, normal flow

SivaComm:Enabled = false — the default. HMS_WEB exactly as it was before SivaComm: the original page with the code and the new password on one screen, the original two requests, HMS_WEB's own WhatsApp settings. SivaComm is never called, and the three-step endpoints answer 404.

3. Failure paths

What each of HMS_WEB's two calls to SivaComm can return, and what the browser does next. “Expired, locked” covers EXPIRED, ATTEMPTS_EXCEEDED, ALREADY_USED and CANCELLED. Resubmitting after a timeout is safe: the same idempotency key makes SivaComm answer CONSUMED again rather than treat it as a replay.

4. Welcome message and delivery receipts

HMS_WEB gets 202 QUEUED before anything is sent, so registration never waits on Meta. Reset codes use the same send path. Meta signs each receipt and SivaComm checks it first; a status never moves backwards.

5. Deployment steps

In order. Meta setup is first only because its approvals take days; steps 2–7 can run before it finishes (with the WhatsApp section empty, SivaComm runs and records each message as not sent). Commands for every step: docs/DEPLOYMENT.md.
